# Agent access with /operator

## Enable access

Type `/operator` at the start of a composer message to enable MonoCode access in that thread. For example, `/operator start two Codex sessions: one to inspect the API and one to review the UI`, or `/operator list my notes`. The slash picker also offers this command. The transcript shows only the request text in a translucent amber bubble; MonoCode removes the command from the request sent to the agent and supplies the local `app` CLI path and instructions on that turn. Later turns in the same thread can use the CLI without repeating `/operator`; other threads receive no CLI instructions or app access. The CLI can act only during an active agent turn. The agent can run the shown `app --help` command for the exact JSON input fields.

## CLI actions

- `models.list` shows available providers, models, settings, and permission modes.
- `sessions.start` opens a tab in the current project with a prompt. Set `placement: "right"` or `placement: "down"` to split the calling session's pane instead; `besideSessionId` selects another visible session pane in the project. Reuse the returned session ID as the next `besideSessionId` to build nested layouts. By default it submits the prompt; set `draft: true` to save it unsent without starting an agent turn. It requires `harness` and `model`, with exact IDs from `models.list`; a missing or unknown harness or model returns an error that names `models.list`, and MonoCode never falls back to the caller's model or the last model picked in the composer. It also accepts effort or other model settings, permission mode, and current checkout or new worktree choice. Set `worktreeCwd` to a path from `worktrees.list` for a specific existing checkout. Use `worktrees.create` to create a worktree on a named new or existing local branch, then pass its path as `worktreeCwd`. Omit `runtimeMode` to inherit the calling session's permission mode, or set it explicitly to override. It returns the new session ID as soon as the pane and prompt are accepted, so the agent can move it into a folder immediately.
- `sessions.start` with `mcp: "none"` starts an omp session without MCP servers, and every later start of that session (a resume) keeps the choice. omp has no switch that turns MCP off, so MonoCode starts it with a settings overlay (`--config`): `disabledExtensions` gets `mcp:<name>` for each server in omp's agent folder `mcp.json` and `.mcp.json`, added to omp's own effective list, and `mcp.enableProjectConfig` is false. MCP servers that omp loads from other tools' user configs or from plugins are not covered. `mcp: "default"` (or no `mcp`) keeps today's start. Other harnesses refuse `mcp: "none"`. A session keeps the choice after a harness switch: other harnesses ignore it, and it applies again when the session switches back to omp. A session that needs Linear or doop must not ask for `none`.
- `sessions.list` shows project sessions and their archived status. `sessions.read` returns up to three recent user/assistant exchanges, with a cursor for older exchanges and a per-message character cap. `sessions.send` submits a follow-up to a session, while `sessions.draft` saves an unsent message for the user to review. Without `whenBusy`, `sessions.send` rejects a busy session. `whenBusy: "steer"` adds the message to the running turn, and `whenBusy: "followUp"` adds it to the session's follow-up queue. A queued follow-up is sent after the turn ends, unless the queue is paused, for example after Stop. A busy Mono's own chat does not accept `whenBusy`. omp reads steering between tool calls; current omp can move a long shell command to the background, so the steer arrives while that command runs. `folders.list` and `folders.move` organize project sessions in sidebar folders, including a new folder.
- `sessions.stop`, `sessions.archive` and `sessions.delete` take a `sessionId` to manage another session in the project. Monos can select an assigned project with `project`. Stop cancels the current turn and pauses queued messages; archive stops and saves the conversation for later restoration; delete stops and permanently removes the conversation. Open files, terminals and worktrees are kept. These actions cannot target the caller, Mono chats, habit runs or orchestration workers. Reuse the same request ID when retrying a call.
- When a Mono successfully stops, archives or deletes a session it is monitoring, its pending completion report for that session is dismissed, including any queued report. The Mono confirms the action in its current reply. Reports for other sessions and other Monos are kept. Rejected launches or follow-ups return a CLI error without a later completion report.
- `monos.list` and `monos.read` let a Mono or one of its habit runs see other Monos. They take a `monoId` instead of a project, so a Mono without projects can use them. `monos.list` returns each Mono's ID, name, role (`giga` or `mono`), projects, busy state, queue length, `queuePaused` (its queue sends nothing until someone resumes it) and whether its chat exists; `self` marks the caller. `monos.get {"monoId"}` returns one Mono the same way, plus the `harness` and `model` its chat runs on (`null` until it has a chat). `monos.read` pages another Mono's chat like `sessions.read`.
- `messages.get_monos`, `messages.send`, `messages.reply` and `messages.get` carry and read messages between Monos, for a Mono chat, one of its habit runs, or a lead or worker session with app access (see Levels and message limits). MonoCode decides the sender, the receiver and the route, and keeps every accepted or rejected `messages.send` and `messages.reply` call as a row in `monocode.db` (refusals such as `invalid_input`, repeated calls, `messages.get_monos` and `messages.get` write none); the agent gives only the text, the target and whether it needs an answer. `messages.get_monos {}` returns `{mono_id, mono_name, role, you}` for each Mono in rail order; `you` marks the caller. `messages.send {"message","send_to","wanting_reply","intent","reply_to"?,"scope"?}` sends to a Mono's chat (`send_to` is its `mono_id`) or to a session in one of the caller's projects (`send_to` is its session ID). `wanting_reply` and `intent` are required and have no default. `intent` `"new"` takes no `reply_to`; it waits until the receiver's running turn ends, or starts a turn when it is idle. `intent` `"steer"` needs `reply_to`, the `message_id` of a message the caller sent to `send_to` (a handle is `invalid_input`); it goes into the turn that runs that message's work, in the session handling it, and is refused with `target_gone` when that work is not running. Or a steer passes `"scope": "turn"` and no `reply_to`: it changes everything the recipient is doing now, in that recipient's own running turn only, never in the sessions it started. A Giga may steer a regular Mono's whole turn, and a regular Mono the whole turn of a lead session in one of its projects. A steer with neither `reply_to` nor `scope` is refused with `steer_needs_target`, and one with both is `invalid_input`. A steer whose turn ends while MonoCode checks it is dropped with a notice to the sender, and `messages.send` answers `status` and `delivery` `"dropped"`. A steer to a project session that cannot join that turn when it arrives (the turn ended, or this window runs none) is dropped with a notice to the sender, and `messages.send` answers `status` and `delivery` `"dropped"`. Its `hop` is the named message's `hop` plus one. A steer that misses that turn before the agent takes it is `dropped`, and the sender gets a notice. `"reply"` and `"continue"` are refused with `intent_not_allowed`: answer with `messages.reply`, and `continue` is for users. `action_type` is gone and is refused as an unknown field. The result has `message_id`, `status` (`open` while it waits for an answer, else `delivered`), `delivery` (`submit`, `queue`, `steer`, or `paused`: the receiver's queue sends nothing until someone resumes it) and `hop`. The receiver reads `<mono_message message_id="…" from="…" mono_id="…" role="…" wanting_reply="…">` around the text. A message that waits for an answer also carries `handle="#n"`, numbered from `#1` in each turn of the receiver. A reply or a steer also carries `reply_to="m_…"`, the `message_id` of the message it refers to, and its text starts with one line that names that message, such as `[steer → #1 · "first words…"]`, `[reply → m_… · "first words…"]` or `[re … · "…"]` for continue: a handle when that message holds one in the receiver's current turn, else its `message_id`, then its first eight words (at most 60 characters). A whole-turn steer starts with `[steer → whole turn]` and has no `reply_to`. A new message has no line, and the queue and the transcript show the text without it. A message the user types into a busy session that joins its running turn reaches the agent with `[steer → whole turn]` before the user's text; the transcript shows the text without it. `messages.reply {"message","to"?,"wanting_reply"?}` answers in the turn that makes the call: without `to` it answers the only open handle, and `to` names the handles to answer, as `"#1"` or a list of 1 to 9 different handles. Each answered message gets its own reply in its sender's chat; the result lists `message_ids` and `answered`, and each answered message becomes `answered`. A message still open when the receiver's turn ends becomes `unanswered`. A message becomes `dropped` when the user removes it from the receiver's queue, when the chat or session it went to is reset, archived or deleted while the message still waits there, or when that session no longer exists when MonoCode starts. A message still waiting for an answer when the chat that sent it is reset, archived or deleted also becomes `dropped`, so a late reply gets `handle_closed`; no notice goes out for it. The sender's Mono then gets `<mono_notice message_id="…" status="unanswered|dropped" to="…">` around the first 60 characters of the message, once, queued in its current chat behind any running turn. Messages are limited to 8000 characters. A call made again with the same request ID and input returns its first result with `duplicate: true` and delivers nothing again; the same ID with other input gets `request_id_reused`. A failed call answers `{"ok":false,"code","hint"}`, and a rejected one also names its stored row in `message_id`. Codes: `invalid_input`, `request_id_reused`, `not_a_mono`, `roster_unavailable`, `too_large`, `unknown_target`, `self_send`, `direction_forbidden` (a session outside the caller's projects, or another Mono's chat), `reply_unsupported_target` (a project session cannot answer, so send it `wanting_reply: false`), `habit_cannot_wait`, `target_no_conversation`, `intent_mismatch` (`new` with `reply_to` or `scope`, `reply` or `continue` without `reply_to` or with `scope`), `steer_needs_target` (a steer with neither `reply_to` nor `scope`), `steer_scope_not_allowed` (the caller may not steer that recipient's whole turn), `nothing_running` (a whole-turn steer to a recipient that runs no turn), `intent_not_allowed`, `unknown_message` (a `reply_to` that names no message the caller can refer to), `steer_target_mismatch` (`reply_to` is not a message from the caller to `send_to`), `cannot_steer`, `no_open_handle`, `ambiguous_reply` (several handles are open and no `to` names one), `unknown_handle` (a `to` handle that this turn did not give), `handle_closed` (a `to` handle that is already answered, unanswered or dropped) and `target_gone` (also for a steer whose work is not running). `no_open_handle`, `ambiguous_reply` and `unknown_handle` list the open handles in `open_handles`. `monos.send` is removed: it answers `action_removed` with the hint `Use messages.send (MCP send_message).` `messages.get {"handle"}` returns `{message: {message_id, from, to, intent, reply_to, body, wanting_reply, status, created_at, handle?}}` for an accepted message that the caller sent or received; `handle` is a `message_id` or a handle such as `"#1"` of the caller's current turn, and the answer has `handle` only when the message holds one in that turn. A handle that names nothing in the turn gets `unknown_handle`; a missing id, a rejected row and a message between two other Monos all get `unknown_message`, so the answer never tells whether such a row exists.
- `messages.ask {"message","send_to","due_minutes"?}` asks the caller's direct child for work: a Giga asks a Mono, a Mono a lead it started, and a lead its own worker; any other target gets `not_direct_child`. The ask is a `messages.send` of `message` to `send_to` with `wanting_reply` false and `intent` `"new"`, and a key in `monocode.db` that the child spends with `messages.ack`. `due_minutes` is the active time the child has, 10 to 480 (else `invalid_input`), default 60; active time counts only while MonoCode runs and the Mac is awake. A Giga's ask has no deadline. The child's `<mono_message>` carries `ask_id="m_…"`, the ask's `message_id`, and, when the ask has a deadline, `due_in="<n>m"`: the active minutes left when the message is handed to its turn, rounded up. `messages.ack {"ask_id","message"}` tells the asker that the work is done and spends the key. Only the Mono or session the ask went to can ack it, once; it is a `messages.send` of `message` to the asker, whose `<mono_message>` carries `ack_of="m_…"`, the `ask_id` it closes. Both answer what `messages.send` answers, and an ask's `message_id` is its `ask_id`. A call made again with the same request ID returns its first result. Codes: those of `messages.send`, `not_direct_child` for `messages.ask`, and `ack_refused` for `messages.ack` when no open ask has that id, the ask was already acked, or it is not the caller's (the hint says which).
- `messages.question {"ask_id"?,"message"}`, `messages.answer {"ask_id","seq","message"}` and `messages.update {"ask_id"?,"message"}` speak on an open ask and keep its key. Each is a `messages.send` of `message` to the other party. The child asks the asker up to 3 questions per ask, one at a time; a question pauses the ask's active clock (no reminder falls due while it waits) and arrives with `question_of` (the ask id) and `seq`. The asker answers with that `ask_id` and `seq`; the answer arrives with `answer_of` and `seq`, and the clock resumes where it paused, so the deadline moves by the active time the question waited. The child sends one update per ask (`update_of`); the clock runs on. Without `ask_id`, a question or update goes on the caller's one open ask (`invalid_input` when it has more than one). A question a parent cannot answer becomes its own question on its own ask, one hop up at a time. Refusals: `question_refused` (not yours, acked, a question already waits, or 3 questions asked), `answer_refused` (not your ask, no question waits, or another seq) and `update_refused` (not yours, acked, or already updated); the hint says which.
- Five active minutes before an ask with a deadline is due, its child gets one hidden prompt `<mono_reminder ask_id="m_…" stage="t5">` that names the ask: as a new turn when it is idle, after the running turn ends when it is busy, or in the running turn of a Mono chat whose harness can steer. The reminder is not a message and cannot be answered; ack the ask with `messages.ack` when its work is done. The reminder also offers the one extension: from then until the deadline the child may call `messages.extend {"ask_id"?}`, which moves the deadline 15 active minutes once and answers `ask_id` and `due_in`. `ask_id` may be left out when the caller has exactly one open ask. An extend by anyone but the child, of an acked ask or a Giga's ask (no deadline), before the reminder, at or after the deadline, or a second time answers `extend_refused` with a hint that says which.
- At the deadline the child gets a second hidden prompt `<mono_reminder ask_id="m_…" stage="deadline">`. Five active minutes later, if the ask is still open, its parent gets `<mono_reminder ask_id="m_…" stage="why" child="<send_to>">`, which names the child to ask why, and MonoCode stores a `miss` for the ask with no reason yet. The child then calls `messages.reason {"ask_id"?,"message"}` to store why the ask is late on that miss; it answers `ask_id`. A reason by anyone but the child, of an acked ask, before the miss, or a second time is refused with `reason_refused` and a hint; an empty or too long `message` gets `invalid_input`. Nothing expires: the ask stays open after the miss, and the child acks it as before. A paused ask gets no reminder and no miss. Each reminder goes out like the five-minute one.
- A Mono chat or habit run on Claude Code, Codex or omp also gets these eleven calls as tools named `get_monos`, `send_message`, `reply`, `get_message`, `ask`, `ack`, `question`, `answer`, `update`, `extend` and `reason`, with the same fields. Claude Code and Codex start the MonoCode executable as the MCP server `monocode` (`<app> app-mcp`); it reads the token from the agent's environment, so the registration never contains it. Codex is told to pass only `MONOCODE_APP_ENDPOINT` and `MONOCODE_APP_TOKEN` to that server. omp gets them as RPC host tools, which also work in Plan mode; an omp that does not support host tools keeps the CLI. The model cannot pass a request id, so each tool call gets one from MonoCode. When MonoCode does not confirm a call in time, the call is sent up to two more times with that same id, which returns the first outcome rather than delivering again. If no attempt is confirmed, the tool answers `outcome_unknown`: the message may already be delivered, and the hint tells the model not to send it again, to check with `get_monos` that MonoCode responds, and to wait for a reply if it asked for one. Codex is given a 180 s tool timeout, longer than the 144 s those retries can take, so it waits for them. Other harnesses use the CLI only: Cursor, Devin, Grok, fx and Antigravity until their MCP path is checked on a machine that has them, Hermes because it removes the token from an MCP server's environment, and Pi and OpenCode because they have no per-session tool path. A Claude Code user who sets `CLAUDE_CODE_MCP_ALLOWLIST_ENV=1` or `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` gets `no_token` from the tools; the CLI still works.
- An app call answers `no_token` when the agent's process has no `MONOCODE_APP_ENDPOINT` or `MONOCODE_APP_TOKEN`, and `app_cli_unavailable` when it comes from an Inbox Ask, an orchestration lead or worker, or a session that is no longer open in MonoCode. Neither suggests a retry.
- `monos.create` and `monos.update` are for Giga Monos only. A Mono is a Giga Mono when the user turns on **Giga Mono** in its settings; Giga Monos have their own section above Monos in the sidebar. Any other caller, including a regular Mono, its habit runs and project sessions, gets code `giga_only`. `monos.create {"name","harness","model","projects":[...],"soul"?,"giga"?:false}` creates a Mono and its chat on exactly that harness and model; both are required (run `models.list` for IDs), and the composer's last model is never used. `projects` names projects in MonoCode by path or name, and `soul` becomes the new Mono's SOUL.md. `monos.update {"monoId","harness"?,"model"?,"name"?,"projects"?}` changes another Mono. `name`, here and in `monos.create`, must have 1 to 256 characters besides outer whitespace, the limit `monocode.db` keeps. A `model` alone must belong to the Mono's current harness, and a `harness` needs a `model`. A busy Mono is left unchanged and the call fails with `mono_busy`; a Mono cannot update itself (`self_update`), and an unknown ID gets `unknown_mono`. `monos.configure` is renamed: it answers `action_removed` with the hint `Use monos.update.`, and `monos.delete` is not an action (`unknown_action`). These refusals, `not_a_mono`, `invalid_input` (also for a `before` that is not a turn ID, and for malformed JSON or request IDs the CLI refuses itself) and `no_conversation` from `monos.list`, `monos.get` and `monos.read`, and `request_id_reused` for a request ID reused with different input, are `{"ok":false,"code","hint","error"}` with `error` equal to `hint`; the CLI adds no `retryWith` to a coded failure. Both return the Mono's ID, name, Giga setting, projects, harness and model.
- `workspace.status {}` is for a Mono or its habit runs. It returns the shared Giga workspace: `root` (`~/MonoCode`), `state` (`ready` or `blocked`, with a `reason` when blocked), `gigaSlug` for a Giga Mono, and `lastEnsure` (`at`, `trigger`, `created`, and `error` when it failed). Project sessions get `Only a Mono or its habit runs can read the workspace`.
- `milestones.list`, `milestones.add`, `milestones.update`, `milestones.remove` and `milestones.reorder` keep a project's roadmap of future goals. A session works in its own project; a Mono or one of its habit runs names one of its projects with `project`, which it may leave out when it has one project. `milestones.list` returns `{project, settings: {enabled, hiddenStatuses}, milestones}`, each milestone with `id`, `title`, `note`, `status`, `target`, `order`, `createdBy`, `createdAt` and `updatedAt`. `milestones.add {"title","note"?,"status"?,"target"?}` adds one; `status` is `idea` (default), `planned`, `in_progress` or `done`, and `target` is a `YYYY-MM-DD` date, or `""` or `null` for later; both store and answer `null`. `milestones.update {"id","title"?,"note"?,"status"?,"target"?}` changes the fields it names (a `target` of `""` or `null` clears the date), `milestones.remove {"id"}` answers `{removed}`, and `milestones.reorder {"ids":[...]}` takes every id of the project in the new order. MonoCode records the caller as the writer (`mono:<id>` or `session:<id>`); `createdBy` and `by` are refused as unknown fields. When the user turns milestones off for a project, the four writes answer code `milestones_off` and change nothing, and `milestones.list` still answers with `enabled: false`. Other codes: `invalid_input`, `unknown_milestone` (an id that is not in this project) and `stale_order` (ids that are not exactly the project's).
- `notes.list` returns titles and short previews; `notes.read` returns one full note by ID.

## Levels and message limits

A session that `sessions.start` started has app access in every turn, without `/operator`: the call stamps its first message with the caller. Until you type `/operator` in it, it cannot start a session with a more permissive `runtimeMode` than its own. On Codex it keeps the sandbox network of its own `runtimeMode`, so outside `full-access` an app CLI call from inside the sandbox cannot reach the app. It gets the Mono messaging tools, which run in the `monocode` MCP server outside the sandbox; outside `full-access`, MonoCode asks you once per session to allow that server's calls; in `auto`, Codex's auto-review decides each call instead. Sessions that a Mono started before this version carry no stamp and keep no app access.

- A session that a lead session starts is that lead's worker. Every other session is a lead. A Mono's start makes a lead.
- A Giga may message any regular Mono. Two Gigas, or two regular Monos, need a project they share, or one of them in the other's `messageAllowlist`, which a Giga sets with `monos.update {"monoId","messageAllowlist":["<mono_id>"]}` (`[]` clears it; `monos.get` shows it); else `direction_forbidden`. A regular Mono messages a Giga with `intent` `"new"`, answers it with `messages.reply`, and steers it only with `reply_to` set to a message that Giga sent it in the last 24 hours that wanted an answer and got none (else `upward_steer_forbidden`), while the Giga chat that sent it runs (else `target_gone`).
- Leads and workers use `messages.*` with the same tools as a Mono chat. A lead may message its own workers and the Monos that have its project. Only its lead may message or steer a worker, and a worker may message only its lead. A lead or worker never asks for an answer, and sends to its lead or a Mono only `intent` `"new"`. The receiver reads `from="<session title>" session_id="…" level="lead|worker"` in place of `mono_id` and `role`.
- Each level refusal is kept as a rejected row, with a hint that names what to do: `worker_cannot_spawn` (a worker calls `sessions.start`), `worker_scope` (a worker calls an action other than `messages.*`, or messages anyone but its lead), `steer_via_lead` (a message, `sessions.send` or `sessions.draft` to a worker from anyone but its lead), `session_cannot_wait` (a lead or worker sends `wanting_reply: true`), `upward_steer_forbidden` (a lead or worker steers its lead or a Mono with `reply_to`) and `lead_scope` (a lead messages another lead or a user session, or a lead that `sessions.start` started calls an action other than `models.list`, `sessions.list`, `sessions.start`, `worktrees.list`, `worktrees.create` or a `sessions.*` action on one of its workers).
- A session's level comes only from its saved `sessions` row (its `lead_session_id`), never from what the call or the window sends. MonoCode saves a session before the first turn that has app access, and `sessions.start` answers only after the new session is saved. `/operator` is refused in a session MonoCode never saves (`~` or a remote project). A session caller with no row gets `unknown_caller`, with no row written. A session the window lists but has not saved is treated as a lead: it has no stored lead link.
- A submitted `sessions.start` answers `message_id`, the record of the new session's first prompt. Pass it as `reply_to` with `intent` `"steer"` to change the work that session runs, while it runs. A draft start has none. A submitted start from a Mono or a lead is also an ask to the new session (its lead or worker). The new session's first prompt is a `<mono_message>` with that `ask_id` and its `due_in`, as for `messages.ask`, and the start also answers `ask_id` (the same id as `message_id`). The new session acks it with `messages.ack` when the work is done. `due_minutes` on `sessions.start` is the ask's active time, 10 to 480, default 60, as for `messages.ask`. A value out of range, or `due_minutes` on a start that is no ask (a Giga's start or a draft), gets `invalid_input` before anything launches. A Giga's start is no ask; a Giga gives a Mono a project with `messages.ask`, which has no deadline. The same start again with the same request ID answers the same session and writes no second ask; the request ID used again with other input, or for a start whose session was archived or deleted, gets `request_id_reused` before anything launches.
- Limits for every sender: 6 `messages.send` calls to one recipient in 10 minutes (`rate_limited`; replies and refused calls do not count), chains of replies and steers 4 deep (`hop_limit`), and 8000 characters (`too_large`).

## Shared Giga workspace

Giga Monos share the git repo `~/MonoCode`. Each Giga has its own folder, `gigas/<gigaSlug>/`, with `AGENTS.md`, `log.jsonl`, `briefs/`, `runbooks/`, `projects/`, `monos/`, `state/` and `scratch/`. The root holds `AGENTS.md`, `.gitignore`, `shared/` and `index/`.

- The slug is set the first time Giga is turned on: the name in lowercase, other characters as `-`, at most 48 characters, with `-2`, `-3` and so on when another Mono has it. A rename keeps the slug.
- Turning Giga on makes `~/MonoCode` the Mono's first project and keeps its other projects. When Giga is turned on and at every ensure, `~/MonoCode` is added to the Projects sidebar the way **Open folder…** adds a folder, once. A project already in the sidebar keeps its place, and an archived `~/MonoCode` stays archived. Sessions it starts go into a sidebar folder named after it. A new Giga chat and every habit run start in its folder. An existing chat keeps its folder, because some harnesses resume a conversation only in the folder where it started.
- At app start, when Giga is turned on, and before every Giga turn and habit run, the app creates what is missing. It never overwrites a file, except the text between `<!-- monocode:managed:start -->` and `<!-- monocode:managed:end -->` in `AGENTS.md`. It never changes `shared/CONVENTIONS.md` after creating it. The managed block of `AGENTS.md` says that `app monos.send` is removed and names `app messages.send` instead, so a workspace whose conventions still name the old action is corrected there. It runs `git init` when needed and installs `.git/hooks/pre-commit`. A pre-commit hook that is not MonoCode's is left as it is. When `~/MonoCode` is a file, or a link to a folder outside the home folder, nothing is changed and the state is `blocked`. Problems show once per app run in the Giga's chat as `Giga workspace: <reason>`, and the turn still runs.
- After every Giga turn and habit run, the app appends one receipt to `gigas/<gigaSlug>/log.jsonl`: `{"v":1,"at":…,"giga":{"monoId","slug"},"sessionId","kind":"chat|habit","asked":"<first 200 characters>","outcome":"completed|failed|cancelled","sent":[{"requestId","toMonoId"}],"started":[{"requestId","sessionId"}],"files":["gigas/<gigaSlug>/…"]}`. `sent` comes from that turn's `messages.send` calls to a Mono, and `started` from its `sessions.start` calls. `files` lists, sorted and relative to `~/MonoCode`, the files in `gigas/<gigaSlug>/` that the turn added or changed since it started, except `log.jsonl`, `state/` and `scratch/`. Then, under the lock `.git/monocode-giga.lock`, it rebuilds `index/index.db`. When the turn changed a file in `gigas/<gigaSlug>/` other than `log.jsonl`, it also commits only `gigas/<gigaSlug>/` without secret-looking files, as `giga(<slug>): <outcome> turn <session>`. A turn that only added its receipt makes no commit. Its line stays in `log.jsonl`, also across an app restart, and goes into the next commit.
- The pre-commit hook reads `MONOCODE_GIGA_SLUG`, which the app gives each Giga's agent process. A Giga may commit its own folder and new files under `shared/`. Without the variable, nothing under `gigas/` can be committed. Secret-looking files are always refused.
- `index/index.db` is SQLite with one FTS5 table, `entries(source, giga, path, at, text)`, built from every `log.jsonl` line and every file in `gigas/*/briefs/`. Example: `sqlite3 ~/MonoCode/index/index.db "SELECT giga, path FROM entries WHERE entries MATCH 'tracing'"`.
